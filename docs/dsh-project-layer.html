在 DeepSeek Harness 上实现 Projects

将 Cursor Projects（3.20–3.27）的三栏交互工作台、Claude Code Projects 的三层记忆与状态收敛机制，装进 DeepSeek 官方 dsh-superagent 的事务与授权引擎。不修改 DSH 宿主源码（app.asar）一行，以纯 Bundle 插件形态交付。

核心结论

Projects 不是「带文件夹的聊天列表」，而是把 Agent 的工作单元从单次会话（Session）提升为持久项目（Project）。壳学 Cursor（左栏平铺项目、中栏常驻协调者、右栏 List | Board | Library）、上下文分层学 Claude Code（Instructions / Memory 索引 / 仓库 AGENTS.md 严格隔离）、底座用 dsh-superagent（单写者 SQLite 事务、Effect 持久化队列、Mandate 授权边界、Local Worktree 并发槽位）。

01背景：为什么「单次会话」撑不起长周期工程？

当开发任务从「修一个函数」变成「跨 15 个 PR 的功能、框架迁移或日常守护」时，传统的「一个任务开一个 Chat」模式会同时撞上三座墙。

痛点一 · 冷启动失忆

每个新会话都在重新摸石头过河

上个会话花了 12 轮才试出「跑集成测试前要先起本地 Redis 容器、鉴权走网关 B」，会话一关知识就锁死在旧聊天记录里。下个会话进来，你得把背景再敲一遍，或者看着 Agent 再踩一遍同样的坑。

痛点二 · 人工调度带宽爆炸

人被迫给十几个并发会话当肉身路由器

并行开 5 个会话改不同模块时，你需要自己切窗口盯谁跑完了、谁卡在权限确认、谁的 CI 挂了、哪两个分支改了同一处配置。并行度超过 3，人的心智负担就超过写代码本身。

痛点三 · 左栏会话坟场

几十个同名会话堆满侧边栏

一周下来左栏攒出 40 个自动命名的会话，分不清哪个是临时提问、哪个是还没合入的半成品分支，也无法把正在进行的分支工作移交给后续任务接着做。

03核心架构修正：为什么 Task (YOU-1) 必须与 Worker 解耦？

Cursor 在 3.26 版本把 Project Notes 正式重构为独立的 Task Tracker。如果把右栏里的任务行直接等同于 dsh-superagent 的 Worker Session，会立刻卡死在以下四个日常场景上。

Layer 1 · 容器

Project（项目）

跨周/跨月存活的顶层作用域。

  • 任务前缀（如 YOU）与自增计数器
  • 唯一常驻协调者 coordinatorSessionId
  • 关联仓库组 repositories[]
  • Git 化的 context/ 记忆目录
Layer 2 · 计划项

Task（YOU-1）

右栏 List / Board 里的工作卡。

  • 支持父子层级 parentTaskId
  • 可处于 Queued（尚未派给任何 Worker）
  • 状态由协调者或关联 Ticket 自动推进
  • 可绑定 specPath 与多个 PR
Layer 3 · 授权执行

Ticket & Assignment

直接复用 dsh-superagent 工作层。

  • 持有不可变 Mandate 授权凭证
  • 分配独立 Git Worktree 与 worker-* 会话
  • 受 WorkerSlots 并发上限与留人槽保护
  • 崩了可换新 Assignment 重试同一 Task
Layer 4 · 可验证产物

PR & Artifact

解决并行后「人评审带宽不足」的交付物。

  • GitHub PR 状态自动追踪（CI / Review / Merge）
  • 超过 1 个 PR 自动折叠为 [N PRs] 胶囊
  • 截图、录屏、调研报告自动归档进 Library

04从 Cursor 3.19–3.27 与 Claude Code 提炼的 6 组交互契约

这些细节全部来自两家过去半年的迭代补丁与社区高频反馈，提前写进规范可以避免后期返工。

契约 01 · 两个入口

极简新建 + 散装会话中途「收编」

  • 极简新建（From Scratch）：弹窗只留 4 项——图标、名称（必填）、一句话北极星 Goal（选填）、关联本地工作区/仓库（选填，允许无仓库纯调研启动）。
  • 中途收编（Add to Project）：你在下方 工作区 普通会话里聊了 20 轮发现是个大活，直接在左栏右键该会话选 加入项目 (Add to Project)。协调者自动读取该会话历史，在项目内生成「建议拆分的 Tasks 与提取的上下文」供你一键确认。
  • 防串味规则（Cursor 3.27）：当焦点在某个 Project 时点左上角全局「＋ 新会话」，新建的是普通独立会话，绝不误继承当前 Project 的后台规则。
契约 02 · 协调者防呆

发送按钮永不变 Stop + 首句秒回 + 内部通信折叠

  • Keep Send, Never Stop（Cursor 3.27）：协调者运行期间，输入框右侧始终保持 Send（追加/插话 steering），避免用户想发第二条指令时顺手点到 Stop 掐断正在派单的协调者。
  • 首句秒回（Cursor 3.26）：协调者收到消息必须先输出一句确认与第一步打算，再调工具读文件或启动 Worker，消除界面假死感。
  • 内部回报单行折叠（Cursor 3.27）：Worker 发给协调者的常规进度折叠为居中单行 Update from YOU-1；只有协调者正式对人说话时，才点亮左栏未读蓝点。
契约 03 · 阻塞解封

主对话输入框上方 Question Tray 直接回答子代理

  • Claude Code 的痛点：子线程卡在提问或权限审批时，跟主协调者说话没用，必须手动点进子线程内部回答。
  • 我们的做法（对齐 Cursor 3.20）：任何后台 Worker 调用 orchestrator_report(human_action) 提问时，主对话输入框上方立即浮出黄色的 Question Tray，标明 Question from YOU-4 及预设选项。
  • 你在主对话窗口直接点击选项或打字回车，插件后端直接通过 Engine 把回答投递给该 Worker 的专属 Thread，零窗口切换。
契约 04 · 精准引用

输入框原生支持 @YOU-1 任务胶囊与 #PR 胶囊

  • 在项目主对话敲 @，自动列出当前项目的 Tasks（按状态排序，与右栏一致），输入编号或标题关键字即可插入 [@YOU-1] 胶囊。
  • 敲 # 搜索并插入项目关联仓库的 PR 或 Issue。
  • 对协调者说「按 @YOU-1 的改法把 @YOU-5 也处理了，合进 #252 同一分支」时，后端直接解析为精确的 ticketId 与 threadKey，零歧义。
契约 05 · 状态收敛

右栏 6 态分组 + 15 秒低成本实时摘要 + Peek 抽屉

  • 状态优先级排序：Waiting on you（黄，等回答/报错）→ For Review（紫/绿，PR 待审）→ In Progress（蓝，运行中）→ Queued（灰，排队中）→ Idle → Done（折叠）。
  • 双速行摘要（Claude Agent View 机制）：Worker 运行中每 15 秒直接取其最新工具动作刷一行状态（0 额外模型调用）；每轮 Turn 结束写一句精炼结论。
  • 空白不扰民（Cursor 3.27）：新建项目尚未产生任何 Task 或 Library 文件时，右栏默认保持收起；第一个 Task 创建瞬间自动滑出。
契约 06 · 生命周期

完整的 Pause / Archive / True Delete 三态控制

  • Pause（一键冻结）：立即中断所有运行中 Worker 轮次、暂停 GitHub/飞书轮询与定时任务，顶部显示 Paused 横幅，点 Resume 恢复。
  • Archive（归档隐藏）：停止所有后台活动与 PR 监听，将项目从左栏移入归档过滤视图，随时可 Unarchive。
  • True Delete（真删除，修补 Cursor 社区头号差评）：二次确认后，彻底删除项目 SQLite 数据、context/ 目录与受管本地 worktree，但绝不删除已推向远端 GitHub 的分支和 PR。

05Library 与三层上下文治理：怎么让项目越用越聪明，而不是变成垃圾场？

记忆系统的共识是「写入门控比检索算法重要」。我们把 Claude Code 的三层边界、Cursor 的 Library 视图与本地 Git 版本控制合在一起。

层级 存放位置 装什么内容 谁能读 谁能写与晋升机制
1. 仓库级规范 各仓库根目录 AGENTS.md / CLAUDE.md 只跟这一个仓库相关的构建、测试、目录结构与代码风格（由 DSH 原生 @deepseek-ai/dsh-agent-instructions 自动加载） 进入该仓库 Worktree 的 Worker 人维护，随代码仓库 Git 提交
2. 项目级常驻索引 <projectDir>/context/INDEX.md 严格限制 ≤ 1,200 tokens：北极星目标（Goal）、关联仓库表、跨仓硬约束、以及指向下方切片文件的检索目录（“改 X 前先读 Y”） 协调者 + 所有 Worker（常驻注入 System Prompt） 人和协调者直接写；Worker 不可直接改 INDEX.md
3. 决策与 Spec 切片 context/decisions/*.md
context/specs/*.md		 每个技术决策或任务拆分方案一个短 Markdown，头部带 YAML：status: active | superseded | disputed、supersedes: ...、source: YOU-1 协调者 + 相关 Worker 按需读取 协调者起草；人在对话中拍板后标为 ratified；旧决策被替代时标 superseded
4. 操作手册（Runbooks） context/runbooks/*.md Worker 摸索出的「怎么跑某服务测试、本地环境坑、验证命令」 仅 Worker 按需读（绝不塞给协调者，防协调者自己下场排障） Worker 调 project_context_propose 写入（初态 proposed）；仅当关联 Ticket 成功 Completed / PR Merged 时才正式转正
5. 工件与参考资料 context/artifacts/*
context/uploads/*		 人拖进项目的参考文档（User files），以及 Worker 产出的回归截图、录屏、性能报告（Project files） 人在右栏 Library 预览；Agent 按路径引用 人拖拽上传，或 Worker 完成任务时附带产出

防污染机制一 · 本地 Git 自动版本化

context/ 目录本身就是一个独立 Git 仓库

新建 Project 时自动在 <stateDir>/projects/<id>/context/ 执行 git init。每次工具写入或巩固自动生成一条带 Task ID / Session ID 的 commit。你在右栏 Library 里不仅能直接手改 Markdown，还能一键看 diff 和回滚任意 Agent 写坏的记忆；未来接云端 Worker 时，直接 git push/pull 即可跨机同步。

防污染机制二 · 证伪与反驳通道（Dispute Channel）

任何过期的经验都必须能被后续 Worker 一键挂起

半年后接口改了，旧 Runbook 变成毒药。当新 Worker 按某篇 Runbook 执行报错时，调用 project_context_dispute(path, reason, output)：该文件立即标为 disputed（后续 Worker 读到时顶部带红色警告），同时在右栏顶部浮出一条待办，人点「用新结论替换 / 删除旧文」即可完成清理。

06工程落地：在 dsh-superagent 上动哪三刀？

我们已经核实了 /private/tmp/dsh-super 的全部源码与本机 DSH 0.2.1-alpha.2 的插槽契约。只需改动以下核心位置，就能把被动值班流水线升级为交互式 Projects 引擎。

第一刀 · 解开入口死锁

新增内建 project-chat Source

现状问题：src/app/tools/main.ts:49 的 orchestrator_route 只能消费落盘的 trigger_id；人在 DSH 打开协调者会话打字走的是 user/message 事件，不产生 Trigger，协调者无法建单。

改法：在 src/app/sessions.ts:114 捕获人在协调者会话发出的 user/message，自动包装为 source='project'、strength='explicit' 的一等 Trigger 写入 Engine.receive，天然继承全套 Mandate 授权与审计链。

第二刀 · 解开拆单死锁

放开 1 Trigger → N Tasks/Tickets

现状问题：src/core/evals.ts:137,311 按 triggerId 做唯一幂等拦截，且 ticketId = key('ticket', evaluation.id)，导致一个需求无法拆成多个并行子任务。

改法：将幂等键改为 (triggerId, taskKey)，ticketId = key('ticket', evaluation.id, taskKey)；同时在 sources/github.ts:69 将线程键改为 github:<owner>/<repo>#<number>，支持单项目挂载多个仓库不串线。

第三刀 · 解开左栏污染

收敛 Workspace 与挂载三栏 UI

现状问题：src/app/sessions.ts:141 为每个 Ticket 的 Worktree 调用 workspaceRegistry.create(cwd)，导致跑 20 个 Ticket 就在 DSH 左栏「工作区」刷出 20 个顶层文件夹。

改法：Worker 会话创建后立即调用 workspaceRegistry.archiveSession(workerSessionId) 从原生左栏「工作区」隐藏（仍可正常后台运行并在右栏点开）；前端在左栏注入扁平 Projects 区，在右栏注册 Project (List | Board | Library) Tab。

  coordinator_session_id TEXT NOT NULL,
  context_dir TEXT NOT NULL,        -- Git 化的 Library 目录
  repos_json TEXT NOT NULL,         -- 关联的本地/远端仓库列表
  state TEXT NOT NULL DEFAULT 'active', -- active | paused | archived
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- 右栏 List / Board 展示的 Task（与 Worker 解耦）
CREATE TABLE project_task (
  id TEXT PRIMARY KEY,              -- 如 "YOU-1"
  project_id TEXT NOT NULL,
  seq INTEGER NOT NULL,
  parent_task_id TEXT,              -- 支持父子任务聚合
  title TEXT NOT NULL,
  summary TEXT NOT NULL DEFAULT '', -- 15s 刷新或完结结论
  status TEXT NOT NULL,             -- queued | in_progress | waiting | review | done
  repo_alias TEXT,                  -- 指向项目下的哪个仓库
  spec_path TEXT,                   -- 关联的 Library spec 路径
  active_ticket_id TEXT,            -- 当前绑定的 dsh-superagent Ticket
  prs_json TEXT NOT NULL DEFAULT '[]',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

-- Library 文件索引（正文留在磁盘 Git 仓库里，支持 grep/diff/手改）
CREATE TABLE project_library_item (
  project_id TEXT NOT NULL,
  rel_path TEXT NOT NULL,           -- 如 "decisions/004-synastry.md"
  scope TEXT NOT NULL,              -- index | decision | runbook | spec | artifact | user
  status TEXT NOT NULL,             -- ratified | proposed | disputed | superseded
  source_task_id TEXT,              -- 溯源：如 "YOU-1"
  tokens INTEGER NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (project_id, rel_path)
);

DSH 客户端无侵入注入清单（src/client/index.tsx）

  • 左栏 Projects 列表：监听 .kB3qhq_regionArea，在其顶部挂载扁平项目列表组件；自动响应 .kB3qhq_wide 折叠态。
  • 普通会话「加入项目」菜单：通过 ctx.slots.register({ name: 'sidebar.workspaces.session.menu.item', id: 'add-to-project' }) 原生注入会话右键菜单。
  • 中栏底部动态胶囊与 Question Tray：通过 ctx.slots.register({ name: 'conversation.input.overlay' }) 与 conversation.composer.dock 注入 [Questions]、[Agents]、[Listening]。
  • 右栏 Project 面板：通过 ctx.sidebarRightTabs.register({ id: 'dsh-projects/project', kind: 'project' }) 注册原生可分屏、可全屏的右栏 Tab。

为什么这套结构最稳？

1. 不丢 dsh-superagent 的 1.5 万行测试资产：Engine 内部的 Gate、Mandate、Effect 重试队列、Outbox 保序和 WorkerSlots 原封不动。
2. 不改 DSH 客户端源码：升级 DSH 版本不会冲掉任何代码，只靠标准插件插槽工作。
3. 本地与云端自然衔接：Library 是标准 Git 仓库，Executor 是独立 Port，现在跑本机 Worktree，以后随时加远端 VM Executor。
